# Auth token storage: access token in memory, refresh token in localStorage

The backend issues a short-lived (15 min) access token and a long-lived (7 day) refresh token, with `POST /auth/jwt/refresh` taking the refresh token in the JSON request body rather than reading it from a cookie. An `httpOnly` cookie would be the more XSS-resistant place to hold the refresh token, but that requires the backend to set and read it as a cookie, which it doesn't do today. Given that constraint, the dashboard keeps the access token in memory only (never persisted) and the refresh token in `localStorage`, accepting the XSS exposure on the refresh token as the pragmatic match to the current API shape. Moving the refresh token to an `httpOnly` cookie is a reasonable hardening step later, but it's a backend change (cookie-setting on login/refresh, CSRF considerations), not just a frontend one.
